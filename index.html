PHP 개발진은 두 취약점 모두에 대해 국제 표준 취약점 평가 체계인 CVSS v4.0[4] 기준 9.2점(Critical)을 부여했으며[5], 위협 인텔리전스 기업 watchTowr를 비롯한 일부 보안 연구 기관은 실제 악용 파급력을 고려해 만점인 10.0점으로 평가했다.[6] 이번 사태가 단순한 소프트웨어 버그를 넘어 유럽 각국 정부 포털, 글로벌 게임 및 전자상거래 플랫폼, 그리고 국내 대형 커뮤니티들의 동시다발적 ‘서버 셧다운(오프라인 전환)’으로 이어진 배경에는 기존의 웹 보안 방어 체계를 무력화하는 세 가지 구조적 치명성이 자리 잡고 있다.[7]

무엇보다 이번 취약점은 워드프레스(WordPress) 플러그인이나 라라벨(Laravel) 프레임워크 같은 애플리케이션 계층의 결함이 아니라 PHP C 언어 코어 엔진의 메모리 할당 및 예외 처리 메커니즘 자체에 내재된 결함이라는 점에서 위험의 차원이 다르다. 특히 아파치(Apache) mod_php[8] 환경에서는 웹 애플리케이션의 코드가 단 한 줄도 실행되기 전인 ‘HTTP 요청 시작(Request Startup) 및 본문 파싱 단계’에서 취약점이 트리거된다. 이는 개발자가 시큐어 코딩 원칙을 완벽히 준수했거나, 사이트에 아무런 기능이 없는 단순한 "Hello World" 페이지만 띄워놓았거나, 심지어 프레임워크 자체의 ‘점검 중(Maintenance Mode)’ 화면을 활성화해 두었더라도 공격자가 인증 없이 단일 HTTP 요청만으로 서버 제어권(웹 워커 권한의 셸)을 탈취할 수 있음을 의미한다.[9]

나아가 PHP2Shell은 과거 인터넷 보안을 뒤흔들었던 Log4Shell(비인증 원격 코드 실행)의 파괴력과 Heartbleed(원격 프로세스 메모리 유출)의 정보 유출 능력을 동시에 결합하고 있다.

공격자는 완전한 원격 코드 실행에 도달하지 않더라도, CVE-2026-109618의 세부 메모리 노출 프리미티브를 악용하여 PHP 워커 프로세스의 힙(Heap) 메모리[10] 영역을 Set-Cookie: PHPSESSID 응답 헤더를 통해 약 67KB 단위로 원격 덤프할 수 있다. 다수의 요청을 순차 처리하는 공유 워커 구조상 이 메모리에는 직전에 다른 정상 사용자들이 전송한 평문 비밀번호, 세션 토큰, 데이터베이스 자격 증명, API 키, 그리고 TLS 개인 키가 고스란히 남아 있어 치명적인 2차 침해로 직결된다.[11]

여기에 패치 배포 직전 발생한 엠바고(Embargo·보도 유예)[12] 붕괴와 사전 유출로 인해 방어자에게 주어져야 할 최소한의 대응 시간조차 증발했다. 공식 패치가 배포되기도 전에 개념증명(PoC)[13] 시연 영상과 기술 분석 문서가 유출되었고, 컨테이너 보안 벤더의 조기 패치 배포 실수로 공격자들이 바이너리 비교(Binary Diffing)를 통해 공격 코드를 완성하면서 패치 공개 6시간여 전부터 이미 야생에서의 실제 공격(In-the-Wild Exploitation)이 관측되었다. 이에 따라 미국 국가안보국(NSA), 유럽연합 컴퓨터비상대응팀(CERT-EU), 영국 국가사이버보안센터(NCSC)는 즉각적인 패치가 불가능한 모든 기관에 대해 “웹사이트를 즉시 인터넷에서 분리(오프라인 전환)하라”는 초강수 권고를 내렸다.[14]

2.1. 코어 엔진의 아킬레스건: zend_bailout()과 session.upload_progress[편집]

일반적으로 PHP는 개별 HTTP 요청을 처리하기 위해 요청 전용 힙(Request Heap)에 메모리를 할당하고, 요청 처리가 끝나면 이를 일괄 해제하여 워커(Worker) 프로세스[21]를 다음 요청에 재사용한다. 문제는 스크립트나 엔진 내부 작업이 설정된 요청당 메모리 한도(memory_limit)를 초과하거나[22] 치명적 오류(Fatal Error)를 만났을 때 발생한다. PHP의 메모리 관리자(Zend/zend_alloc.c)는 할당 실패 시 zend_mm_safe_error()를 호출하고, 이는 곧바로 zend_bailout()을 실행한다. zend_bailout()은 C 표준 라이브러리의 비지역 점프 함수인 longjmp()를 사용하여 현재 실행 중인 함수 호출 스택을 즉각 탈출하고 최상위 에러 처리 경계로 점프해 버린다.[23]

사용자 정의 PHP 스크립트가 실행 도중 종료될 때는 이러한 급작스러운 점프가 큰 문제를 일으키지 않는다. 그러나 코어 엔진의 저수준(Low-level) C 루틴이 내부 데이터 구조체(해시테이블 리사이징, 문자열 확장, 세션 역직렬화, OPcache 공유 메모리 기록 등)를 수정하거나 라이브 포인터(Live Pointer)를 다루는 도중에 정확히 메모리가 고갈되면 치명적인 결함이 발생한다. longjmp()는 호출자(Caller)로 절대 복귀하지 않으므로, 메모리 할당 직후 실행되어야 할 포인터 갱신, 북키핑(Bookkeeping) 상태 리셋, 그리고 예외 복구 코드가 통째로 생략(Skip)된다.

공격자가 인증이나 애플리케이션의 협조 없이도 이 저수준 엔진 루틴에 도달하여 정밀하게 메모리 고갈을 유발할 수 있는 통로가 바로 session.upload_progress 기능이다.[24] PHP 5.4.0부터 기본 활성화된 이 기능은 사용자가 multipart/form-data 형식의 POST 요청에 PHPSESSID와 PHP_SESSION_UPLOAD_PROGRESS 필드를 포함해 전송하면, 메인 PHP 스크립트가 컴파일되거나 실행되기 이전에 멀티파트 파서(main/rfc1867.c)가 자동으로 세션 콜백을 호출한다. 이 핸들러는 매 업로드 이벤트마다 세션 데이터를 열고, 역직렬화(Decode)하며, 진행 상태 배열을 삽입하고 다시 인코딩하여 기록하는 과정에서 다수의 동적 메모리 할당을 수행한다. 공격자는 멀티파트 요청의 파트(Part) 개수, 필드 및 파일명의 길이, 헤더 반복 횟수를 정교하게 조작함으로써 애플리케이션 코드가 시작되기도 전에 원하는 정확한 엔진 코드 위치에서 memory_limit 초과와 longjmp()를 강제로 발동시킬 수 있다.[25]

2.2. CVE-2026-109618: OOM 메모리 오염을 통한 RCE 및 Heartbleed급 메모리 유출[편집]

CVE-2026-109618(GHSA-w8hw-w9fx-j79w)은 메모리 부족(Out-Of-Memory, OOM) 상황에서 longjmp()가 실행될 때 요청 메모리가 부분적으로만 초기화되거나 오염된 상태로 남겨지고, 직후 이어지는 요청 종료 및 정리(Request Shutdown/Cleanup) 프로시저가 이 잘못된 메모리를 정상 데이터로 신뢰하여 읽거나 분기(Branch)하면서 발생한다.[26] PHP 보안 권고문에 따르면 공격자는 웹 서버의 일반적인 업로드 용량 제한(post_max_size, max_file_uploads)을 우회하여 OOM을 확정적으로 유발할 수 있는 네 가지 정교한 전략을 구사한다.[27] 첫째로 유효한 Content-Length 선언이 없는 멀티파트 요청을 전송하여 초기 post_max_size 검사를 우회하고 디코딩된 본문 데이터를 지속적으로 주입하는 전략이 사용된다. 둘째로 단일 멀티파트 파트 내부에 수천 개의 MIME 헤더를 삽입하는 헤더 플러딩(Header Flooding) 기법이 동원되는데, 이는 네트워크 전송 시의 텍스트 크기보다 PHP 엔진 내부에서 이를 파싱해 구조체로 보관할 때 소비하는 메모리가 기하급수적으로 크다는 점을 이용해 작은 패킷 크기로도 post_max_size 한도 내에서 memory_limit을 손쉽게 고갈시킨다. 셋째로 내용이 비어 있는 파일 입력 필드는 PHP의 max_file_uploads 개수 제한에 카운트되지 않으면서도 표준 파일 메타데이터 배열을 생성한다는 점을 노려, 빈 파일 컨트롤 배열에 깊게 중첩된 필드명(Nested Field Names)을 결합해 배열 생성 작업량과 메모리 소비량을 폭증시킨다. 넷째로 정상적인 요청 시작 이후 애플리케이션 로직 내부에서 공격자 입력에 의해 반복적인 대규모 메모리 할당이 일어나는 경로를 직접 타격할 수도 있다.

풀이

원문은 OOM을 일으키는 네 가지 전략을 개념적으로만 적고 있다. 이 페이지도 그 설명만 옮겼으며, 요청 본문 예시나 페이로드는 싣지 않았다.

원문 내용을 쉽게 정리한 안내이며 새로운 사실은 없다.

보안 기업 Wiz Research와 Imperva, Sansec의 기술 분석을 종합하면, CVE-2026-109618은 실제 공격에서 두 가지 핵심 프리미티브(Primitive)로 작동한다. 첫 번째 프리미티브는 업로드 진행률 역직렬화기 해제 후 재사용(Upload-Progress Unserializer UAF)이다. RFC1867 멀티파트 요청 파싱 중 세션 모듈이 업로드 진행 데이터를 디코딩할 때, 역직렬화기는 요청 소유의 북키핑 정보를 전역 구조체인 BG(unserialize)에 저장한다. 이 순간 OOM이 발생해 요청 힙이 파괴되면 BG(unserialize)의 전역 상태가 리셋되지 않은 채 공개(Published) 상태로 남는다. 동일한 워커가 처리하는 후속 요청에서 PHP는 공격자가 재점유(Reclaim)해 조작한 메모리를 유효한 역직렬화기 북키핑 데이터로 취급하며, 이를 통해 메모리 오염 및 비인증 원격 코드 실행이 달성된다.[28]

두 번째 프리미티브는 원격 프로세스 메모리 유출(Remote Process-Memory Disclosure)이다.

멀티파트 요청 시작 단계에서 업로드 진행률 핸들러는 세션 상태를 조기에 초기화하고 세션 ID 포인터를 PS(id)에 게시한다. 직후 OOM으로 요청이 중단되면 요청 힙은 해제되지만 PS(id)는 해제된 메모리를 가리키는 댕글링 포인터(Dangling Pointer)[29]로 남는다. 후속 멀티파트 요청이 동일 워커에 도달하면, 정상적인 세션 초기화가 이 포인터를 리셋하기 전에 업로드 진행률 정리 경로가 먼저 실행된다. 결과적으로 PHP는 이 오염된 포인터와 조작된 길이 값을 살아있는 zend_string으로 신뢰하여, 워커 힙 메모리 약 67KB를 URL 인코딩한 뒤 클라이언트에게 반환되는 Set-Cookie: PHPSESSID 응답 헤더에 담아 그대로 유출한다. 이 과정은 웹 애플리케이션이 session_start()를 전혀 사용하지 않아도 무조건 동작하며, 공격자는 이를 통해 ASLR(주소 공간 배치 난수화)[30]을 우회할 메모리 주소를 획득할 뿐만 아니라 타 사용자의 세션 토큰, DB 비밀번호, API 키, TLS 개인 키를 손쉽게 탈취할 수 있다.[31]

파인만 풀이

왜? 정리하다 만 "이름표"가 다음 손님의 쿠키에 붙어서 밖으로 나간다.

창고 선반 주소를 적은 쪽지를 손님이 들고 나가는데, 그 쪽지에 적힌 칸에는 사실 다른 손님의 짐이 들어 있다. 원문이 말하는 PHPSESSID 헤더를 통한 약 67KB 유출은, 그 쪽지(포인터와 길이)가 응답 쿠키에 실려 나가는 그림으로 이해할 수 있다. 구체적인 요청 만드는 법은 이 풀이에 없다.

쉽게 풀어 쓴 비유 설명이며, 취약점에 관한 새로운 사실은 담고 있지 않다.

2.3. CVE-2026-109619: 잔류 전역 상태(Stale Global State)를 통한 RCE 및 OPcache 오염[편집]

CVE-2026-109619(GHSA-6wmf-4rv5-p3rp)는 지속성 워커 프로세스(Persistent Worker Process)가 여러 요청을 순차적으로 처리할 때, 이전 요청(Request #1)에서 생성된 내부 상태 포인터가 메모리가 해제된 이후에도 전역 영역에 살아남아 다음 요청(Request #2)의 정상 초기화(php_request_startup()) 이전에 소비되면서 발생하는 교차 요청(Cross-Request) 취약점이다.[32] 공식 권고문은 이를 생산자(Producer)와 소비자(Consumer)의 결합 구조로 설명한다.

먼저 생산자(Request #1) 단계에서 에러, 세션, 객체, 확장 모듈의 전역 상태가 개별 요청 힙 메모리를 가리키도록 설정된 후, OOM이나 구문/컴파일 에러, require 실패, 최대 실행 시간 초과(Maximum execution time exceeded) 같은 치명적 오류로 인해 대응하는 리셋 함수가 호출되기 전에 중단되거나, 요청 종료 후 서버 정리 단계에서 발생한 비치명적 진단 메시지가 이미 비워진 에러 상태를 다시 채워 넣는다. 이어 소비자(Request #2) 단계에서 동일한 워커가 다음 요청을 받을 때, 표준 초기화 함수인 php_request_startup()이 전역 상태를 초기화하기 이전에 실행되는 초기 루틴들이 이 불량 포인터를 역참조한다. 확인된 대표적 초기 소비자는 .htaccess나 FastCGI PHP_VALUE를 통해 전달된 잘못되거나 지원 중단(Deprecated)된 INI 설정(auto_detect_line_endings, filter.default, mbstring, open_basedir 등)을 처리할 때 발생하는 조기 경고/진단 루틴과 session.upload_progress 초기화 루틴이다.

이 메커니즘 아래에서 작동하는 세 번째 핵심 공격 프리미티브는 치명적 오류 백트레이스 해제 후 재사용(Fatal-Error Backtrace UAF)이다. PHP 8.5에서 활성화된 fatal_error_backtraces 기능은 가장 최근 발생한 치명적 오류의 백트레이스를 실행기 전역 변수인 EG(last_fatal_error_backtrace)에 보관한다. OOM 치명적 오류 발생 시 PHP는 EG(last_fatal_error_backtrace)를 초기화하지 않은 채 요청 힙을 파괴한다. 살아남은 워커가 다음 요청의 극초기 단계(실행기 재초기화 이전)에서 INI 진단 메시지 등을 출력하면 이 댕글링 포인터에 접근하게 되며, 공격자가 재점유한 메모리를 따라가며 백트레이스를 갱신하거나 파괴하는 과정에서 제어 가능한 메모리 오염 및 RCE가 발생하며 이는 드루팔 최신 버전(drupal:latest)에서 비인증 RCE로 완벽히 시연되었다.[33]

네 번째 핵심 공격 프리미티브는 OPcache 타입 혼동(Type Confusion) 및 임의 파일 읽기(Arbitrary File Read)다. OPcache는 컴파일된 PHP 구조체를 공유 메모리에 영속화(Persist)하고 워커별 런타임 포인터 맵의 인덱스를 할당한다.

zend_accel_script_persist() 실행 중 PHP는 프로세스 로컬 경계값인 CG(map_ptr_last)를 먼저 전진시키고, 영속화가 끝난 뒤에야 공유 경계값을 게시한다. 만약 이 두 시점 사이에 메모리 할당 실패(OOM) 베일아웃이 발생하면 로컬 경계값만 전진된 채 남아, 공유 상태에서는 여전히 ‘비어 있음’으로 간주되는 슬롯을 부분 영속화된 객체가 참조하게 된다. 이후 다른 워커가 해당 슬롯을 전혀 다른 런타임 객체 용도로 재사용하면 교차 워커 간 타입 혼동(Type Confusion)이 발생하여 공유 OPcache 상태가 오염되고 비인증 RCE로 이어지며, 이는 워드프레스 최신 버전(wordpress:latest)에서 시연이 확인되었다.[34] 또한 Imperva 분석에 따르면, 메모리 베일아웃으로 인해 할당되었으나 게시되지 않은 OPcache 클래스 캐시 슬롯을 재사용해 클래스 상수(Class Constant) 해석을 하이재킹할 경우, 해당 상수에 의존하는 파일 작업의 경로를 공격자가 지정한 경로로 리다이렉트하여 워커 권한 내의 모든 설정 파일과 인증서를 탈취하는 임의 파일 읽기(Arbitrary File Read) 공격까지 가능하다.[35]

파인만 풀이

왜? 어제 손님이 남긴 이름표를 오늘 아침 청소 전에 새 손님이 먼저 집어 든다.

식당 테이블을 치우기 전에 다음 손님이 앉으면, 이전 손님의 영수증이 새 주문서처럼 쓰일 수 있다. 원문의 "생산자(Request #1) / 소비자(Request #2)"는 그 순서를 가리킨다. OPcache는 여러 홀이 하나의 공유 메뉴판을 보는 것과 같아서, 한 홀에서 메뉴판이 바뀌면 다른 홀도 영향을 받는다.

쉽게 풀어 쓴 비유 설명이며, 취약점에 관한 새로운 사실은 담고 있지 않다.

2.4. 양대 취약점 기술 사양 비교 및 업스트림 패치(01a40e89fb) 구조[편집]

PHP 코어 개발진(Arnaud Le Blanc 등)은 단일 커밋 01a40e89fb(“Avoid state corruption via bailout”)를 통해 두 취약점을 동시에 해결했다.[36] 이 패치는 OOM 발생 시 즉각 longjmp()를 호출하던 기존의 복구 불가능한 중단 방식을 폐기하고, 가상머신(VM)의 다음 안전한 지점(Safe Point)에서 실행을 멈추는 지연된 소프트 OOM(Soft OOM)과, 메모리 소비가 그보다 높은 2차 임계치를 넘을 경우 정리 루틴 없이 프로세스를 즉시 강제 종료(_exit())하는 하드 OOM(Hard OOM)의 2단계 구조로 아키텍처를 전면 개편했다.[37]

3. 서버 구동 환경(SAPI)별 위험도 매트릭스 및 글로벌 노출 지표[편집]

PHP가 웹 서버와 통신하는 인터페이스인 SAPI(Server Application Programming Interface) 아키텍처에 따라 공격의 난이도와 전제 조건에는 중요한 차이가 존재한다. 그러나 PHP 개발진과 CERT-EU는 “웹 요청을 처리하는 모든 PHP 설치 환경이 위험에 노출되어 있다”고 명시했다.[40]

3.1. SAPI 아키텍처별 취약성 및 작동 조건 분석[편집]

가장 치명적인 위험군으로 분류된 환경은 아파치 웹 서버의 내장 모듈 방식인 Apache mod_php (prefork MPM)이다. mod_php는 요청 시작(Request Startup) 단계에서 자동 본문 파싱 도중 OOM이 발생해 시작 자체가 실패하더라도, 무조건 요청 종료(Request Shutdown) 프로시저를 호출하는 구조를 가지고 있다. 또한 .htaccess나 아파치 디렉터리 설정(php_value, php_flag)을 php_request_startup() 이전에 적용한다. 따라서 mod_php 환경에서는 백엔드에 어떤 애플리케이션이 깔려 있는지와 무관하게, 외부 공격자가 조작된 HTTP 패킷을 보내는 것만으로 애플리케이션 코드가 실행되기도 전에 CVE-2026-109618과 CVE-2026-109619 양쪽 모두에서 100% 검증된 비인증 원격 코드 실행이 달성된다.[41] 현대적인 Go 기반 앱 서버인 FrankenPHP 역시 요청 시작 실패 시 요청 종료 프로시저를 무조건 호출하는 동일한 구조를 취하고 있어 애플리케이션 독립적인 공격에 취약할 가능성이 높은 것으로 판정되었다.[42]

반면 현대 리눅스 배포판(AlmaLinux 8/9/10, Ubuntu, Debian 등)과 Nginx 환경의 표준인 PHP-FPM (FastCGI Process Manager)[43]의 경우 미묘하지만 중요한 아키텍처적 차이가 있다.

PHP-FPM은 요청 시작 단계에서 OOM 등으로 실패가 발생하면 요청 종료 프로시저를 실행하는 대신 해당 자식 워커 프로세스를 즉각 종료(Terminate)하고 풀(Pool)에서 제거해 버린다. 이 동작 덕분에 요청 시작 단계만 악용하는 단순한 CVE-2026-109618 독립 익스플로잇은 차단된다. 그러나 이것이 PHP-FPM의 안전을 의미하지는 않는다.

첫째, CVE-2026-109619의 경우 동적 FPM 풀 환경에서 session.upload_progress가 애플리케이션 실행 도중 상태를 게시한 뒤 애플리케이션 내부 작업에서 OOM이나 치명적 오류가 발생하면, 워커가 죽지 않고 살아남아 후속 업로드 진행률 요청에서 댕글링 포인터를 소비함으로써 완전한 비인증 RCE가 작동함이 공식 검증되었다. 둘째, 앞단의 Nginx나 Apache(mod_proxy_fcgi)가 PHP_VALUE 또는 PHP_ADMIN_VALUE FastCGI 파라미터를 통해 경고를 유발하는 설정을 전달하는 경우 FPM에서도 조기 INI 진단 소비자가 그대로 활성화된다.

셋째, 정상적인 요청 시작이 완료된 이후 애플리케이션 코드 경로에서 OOM이 유도되면 CVE-2026-109618의 오염된 종료 루틴이 FPM에서도 동일하게 실행되며, PHPSESSID 쿠키를 통한 프로세스 메모리 유출 역시 mod_php와 PHP-FPM 양쪽 모두에서 완벽하게 작동한다.

실제로 연구진은 워드프레스(7.1.2), 드루팔(11.4.3), 줌라(6.1.4), 마젠토(2.4.9), 라라벨(13.11), 심포니(8.1), 미디어위키(1.46.2), 넥스트클라우드(35.0.1), phpMyAdmin(5.2.3), 라운드큐브(1.7.4), WHMCS 등 11개 주요 플랫폼의 기본 설치 환경에서 비인증 RCE를 모두 성공시켰다.[44]

3.2. 글로벌 노출 텔레메트리와 ‘지원 종료(EOL) 절벽’의 역설[편집]

이번 사태가 장기적인 보안 재앙으로 번질 수밖에 없는 구조적 이유는 전 세계 PHP 서버의 버전 분포와 은폐된 공격 표면(Attack Surface)에 있다. 팔로알토 네트웍스(Palo Alto Networks)의 Cortex Xpanse가 수집한 글로벌 공격 표면 텔레메트리에 따르면, 전 세계 공인 인터넷에 노출된 잠재적 취약 PHP 인스턴스는 무려 2,260만 개 이상에 달한다.[46] 또한 구글 산하 바이러스토탈(VirusTotal)이 자체 스캔 데이터를 통해 프로파일링한 결과, 고유 IP 주소 기준으로 약 510만 개의 호스트가 PHP를 구동 중이며 이 중 최소 하나 이상의 포트가 외부에 열려 있는 호스트가 380만 개로 집계되었다.[47]

이 글로벌 텔레메트리 데이터에서 도출되는 첫 번째 심층 위험 요인은 ‘80%의 은폐된 사각지대(Hidden Footprint)’이다. 바이러스토탈이 식별한 510만 개의 PHP 서버 중 HTTP 응답 헤더(X-Powered-By: PHP/8.3.35 등)를 통해 자신의 버전을 외부에 알리는 서버는 약 110만 개(약 20%)에 불과하다. 나머지 약 80%(5대 중 4대)의 서버는 expose_php = Off 설정이나 리버스 프록시 헤더 제거를 통해 PHP 구동 사실과 버전을 숨기고 있다. 많은 기업 보안팀이 단순 배너 그래빙(Banner Grabbing) 스캐너에 의존해 자산의 취약 여부를 점검하지만, 공격자들은 PHPSESSID 쿠키 구조나 워드프레스(53.8만 IP), 라라벨(14.1만 IP), 넥스트클라우드(10.7만 IP), 라운드큐브 및 phpMyAdmin(2.5만 IP)의 애플리케이션 시그니처를 통해 은폐된 PHP 서버를 정확히 찾아내 타격하고 있다.[48]

두 번째 위험 요인은 ‘지원 종료(EOL) 버전의 패치 절벽’이다. 버전 배너를 공개한 약 111.8만 대의 서버를 분석한 결과, PHP 프로젝트로부터 공식 바이너리 보안 업데이트를 제공받는 지원 브랜치(PHP 8.2~8.5)를 구동 중인 서버는 약 27만 2,000대에 그쳤으며, 그중에서도 이번 사태 직전 최신 패치 수준(9월 24일 자 릴리스)을 유지하고 있던 서버는 단 8만 5,000대뿐이었다.[49][50]

반면 session.upload_progress가 기본 탑재되어 취약점에 그대로 노출되면서도 공식 지원이 이미 종료(EOL)된 PHP 5.4부터 8.1 사이의 버전을 구동 중인 서버는 약 75만 8,000대로, 취약 대상(5.4~8.5 구동 103만 대)의 73.6%(쇼단 기준 전체 배너 노출 서버의 약 60% 이상)를 차지한다. 특히 PHP 7.4(약 18.7만 대)와 10년 전에 출시된 PHP 5.4(약 11.9만 대)가 여전히 막대한 비중을 차지하고 있어, 소스 코드 직접 컴파일이나 상용 LTS 벤더의 백포트 없이는 영구적인 무방비 상태(Forever-day)에 놓이게 된다.[51][52]

세 번째 위험 요인은 ‘메모리 유출과 개방형 관리 포트의 치명적 결합’이다. 바이러스토탈 텔레메트리는 PHP가 구동 중인 호스트 중 39만 4,000대가 SSH(22번 포트)를, 23만 3,000대가 MySQL(3306번 포트)을, 그리고 6만 8,000대가 원격 데스크톱인 RDP(3389번 포트)를 인터넷에 동시에 개방하고 있음을 밝혀냈다. 이는 만약 PHP-FPM 환경의 메모리 레이아웃 차이로 인해 공격자의 RCE 시도가 즉각 성공하지 못하더라도, 공격자가 훨씬 단순하고 신뢰성이 높은 CVE-2026-109618의 Heartbleed형 메모리 유출 공격(PHPSESSID 쿠키 덤프)이나 OPcache 임의 파일 읽기 공격을 먼저 수행하여 메모리에 상주하는 DB 접속 계정, SSH 암호, API 키를 추출한 뒤, 외부에 열려 있는 22번(SSH)이나 3306번(MySQL) 포트로 직접 로그인하여 서버를 완벽히 장악할 수 있음을 시사한다.[53] 흥미롭게도 NOX Stealer나 BOMBAY 같은 악성코드 C2(명령 및 제어) 패널을 운영하는 사이버 범죄자들의 서버 약 5,700대 또한 취약한 PHP 버전 위에서 구동되고 있어 공격자 인프라 자체도 역공격에 노출된 상태다.[54]

4. 사태의 이면: PHP 재단의 ‘구조적 실패’와 프론티어 AI가 촉발한 익스플로잇 변곡점[편집]

이번 PHP2Shell 대란은 단순히 코드 결함 하나가 우연히 발견된 사건이 아니다. 그 이면에는 오픈소스 거버넌스의 의사결정 마비, 프론티어 인공지능(AI) 모델에 의한 취약점 무기화 속도의 기하급수적 단축, 그리고 글로벌 보안 엠바고 체계의 붕괴라는 세 가지 거대한 구조적 충격파가 자리 잡고 있다.[55]

4.1. 2024년 외부 감사 이후 2년간의 방치: PHP 재단이 고백한 ‘구조적 실패’[편집]

PHP 재단(The PHP Foundation)이 2026년 10월 21일 발표한 공식 성명에 따르면, 사실 CVE-2026-109618의 근본 원인인 OOM longjmp 문제는 이미 2024년에 처음 포착되었다.[56]

2024년 당시 PHP는 소버린 테크 에이전시(Sovereign Tech Agency)의 자금 지원과 OSTIF의 주선으로 보안 기업 Quarkslab으로부터 수년 만의 첫 외부 보안 감사를 받았다. Quarkslab이 보고한 이슈 중 하나를 수정하던 PHP 재단 계약 코어 개발자가 OOM 처리 과정의 메모리 오염 징후를 처음 발견했고, 당시에도 이론적인 익스플로잇 가능성이 제기되었다.

그러나 당시에는 이를 실제 원격 코드 실행으로 연결할 구체적인 공격 벡터가 증명되지 않았고, 이 문제를 근본적으로 고치기 위해 제시된 여러 설계 대안들이 모두 심각한 트레이드오프(하위 호환성 파괴, 새로운 서비스 거부(DoS) 취약점 유발 가능성, 혹은 수많은 서드파티 C 확장 모듈의 코드 수정 강제)를 수반했다. 결정적으로 당시 PHP 보안팀은 ‘전원 합의제(Strict Consensus)’로 운영되고 있었기 때문에 잘못된 선택이 생태계에 미칠 파장을 두려워하여 어느 한쪽으로도 결론을 내리지 못했고, 엔진 내부를 깊이 이해하는 소수의 코어 개발자들이 다른 업무에 치이면서 패치 작업은 약 2년 동안 멈추고 재개되기를 반복했다. PHP 재단은 이를 두고 “보안팀의 의사결정 프로세스와 리소스 부족이 결합된 명백한 구조적 실패(Structural Failure)”라고 이례적으로 솔직하게 시인하며, 향후 보안팀의 의사결정을 전원 합의제에서 다수결(Majority) 체제로 전환하겠다고 발표했다.[57]

파인만 풀이

왜? 고치려면 엔진을 크게 손봐야 하는데, 다들 합의를 못 해 손이 멈췄다.

오래된 다리의 균열을 발견했지만, 보수 공법이 통행을 막거나 다른 다리를 건드릴 수 있어 위원회가 결론을 못 낸 채 2년을 보낸 꼴이다. 원문은 이를 "구조적 실패"라고 재단이 스스로 시인했다고 적는다.

쉽게 풀어 쓴 비유 설명이며, 취약점에 관한 새로운 사실은 담고 있지 않다.

4.2. 프론티어 AI의 등장: ‘이론적 버그’가 1주일 만에 ‘실전 RCE 무기’로 바뀌다[편집]

인간 전문가들이 “실제 익스플로잇 체인을 구성하기에는 메모리 조작 복잡도가 너무 높다”며 2년간 미뤄두었던 이 난제를 단숨에 돌파한 것은 2026년 중반 투입된 프론티어 AI 보안 모델들이었다. 2026년 7월 30일, 오픈AI(OpenAI)의 대규모 오픈소스 보안 프로젝트인 *‘Patch the Planet’*의 일환으로 캘리포니아 소재 보안 연구 기업 Calif(연구원 Ryan Austin, lcfr-hax)가 PHP 감사를 시작했고, 불과 12일 만인 8월 11일에 2024년의 그 OOM 결함으로부터 무조건부 비인증 RCE를 달성한 보고서를 제출했다.[58] 놀랍게도 같은 날 오픈AI 자체 보안팀(Codex Security / Daybreak Red) 역시 독립적으로 동일한 근본 원인을 찾아내 보고했다.[59] 이어 8월 19일에는 클라우드 보안 기업 Wiz Research가 자체 에이전트인 Wiz Atlas와 구글의 Gemini 4 Argon, 그리고 오픈AI의 GPT-5.6 Sol을 결합하여 동일한 취약점 군을 독자적으로 발굴했다.[60]

여기서 주목해야 할 핵심 통찰은 AI가 수행한 역할의 본질이다. Calif 연구진은 단순한 프롬프트만으로 AI가 모든 버그를 마법처럼 찾아낸 것이 아니며, PHP의 20년 역사와 아키텍처에 대한 인간 전문가의 도메인 지식이 결합되었음을 강조했다. 그러나 일단 취약한 원시 결함(Primitive)이 식별된 이후, 이를 실제 작동하는 RCE 익스플로잇으로 변환하는 과정에서 AI는 무서운 파괴력을 발휘했다. 교차 요청 간 힙 레이아웃을 정밀하게 정렬(Heap Feng Shui)하고, ASLR을 우회하며, 워커 충돌을 피해 제어 흐름을 탈취하는 작업은 과거 세계 최고 수준의 인간 보안팀이 매달려도 수개월이 걸리던 영역이었다. 하지만 Wiz 연구진은 Gemini 4 Argon과 GPT-5.6 Sol을 활용해 디버깅 실패 원인을 실시간 분석하고 다양한 PHP 버전과 메모리 레이아웃에 맞춰 익스플로잇을 자동 보정함으로써, 취약점 발견 이틀 만인 8월 20일에 드루팔 RCE를, 8월 21일에 워드프레스 RCE를 성공시키며 단 1주일 만에 11개 주요 플랫폼을 관통하는 통합 익스플로잇(php2shell)을 완성했다.[61] 즉, AI가 ‘취약점 발견에서 실전 무기화까지의 장벽’을 완전히 허물어버린 것이다.[62]

풀이

원문은 AI가 익스플로잇을 자동 보정했다고 서술하지만, 구체적인 페이로드나 코드는 싣지 않았다. 이 페이지도 그 서술만 옮긴다.

원문 내용을 쉽게 정리한 안내이며 새로운 사실은 없다.

4.3. 엠바고 붕괴와 패치 전 제로데이(0-Day) 공격의 발생[편집]

다수의 연구팀이 동시에 취약점을 발견하고 OS 배포판 및 클라우드 벤더들과 사전 패치 공유가 진행되면서, 당초 2026년 10월 22일 14:00 UTC로 예정되었던 비밀 유지 협약(Embargo)은 세 차례의 연쇄적인 사고를 거치며 통제 불능 상태로 무너졌다.[63] 첫 번째 유출은 10월 20일 15:00 UTC경 해커뉴스(Hacker News) 포럼과 소셜미디어 X에 두 개의 CVE 식별 번호와 함께 “CVSS 10.0짜리 PHP RCE 패치가 예고되었다”는 정보가 게시되었다가 삭제되면서 시작되었다. 이에 PHP 보안팀은 19:30 UTC에 긴급 사전 공지를 띄우고 패치 배포 일정을 하루 앞당긴 10월 21일 14:00 UTC(한국시간 21일 23:00)로 변경했다.[64]

그러나 불과 30분 뒤인 10월 20일 20:00 UTC경 두 번째 대형 유출 사고가 터졌다. 취약점 발견사 중 하나인 Calif가 실제 라이브 타겟을 상대로 php2shell 익스플로잇이 작동하는 개념증명(PoC) 시연 영상을 실수로 웹에 게시한 것이다.[65] 영상은 즉시 삭제되었으나 이미 사본이 해커 커뮤니티에 퍼져 외부의 PoC 개발을 가속화시켰고, 같은 날 23:00 UTC경에는 핵심 인프라 사업자들에게만 전달된 임시 완화 지침이 유출되었으며, 21일 02:29 UTC에는 상세 기술 라이트업(Write-up) 아카이브가 바이러스토탈에 업로드되었다.[66] 결정적인 세 번째 붕괴는 공식 패치 공개를 6시간 이상 앞둔 10월 21일 07:41 UTC에 발생했다.[67] 컨테이너 보안 기업 Chainguard가 엠바고를 일방적으로 파기하고 패치가 적용된 PHP 컨테이너 이미지를 공개 레지스트리에 배포해 버린 것이다.[68] 이로 인해 공격자들은 공식 발표 전에 패치 전후 바이너리를 비교(Diffing)하여 정확한 취약 지점을 역추적할 수 있게 되었고, 불과 2분 뒤인 07:43 UTC부터 클라우드플레어(Cloudflare)와 watchTowr의 글로벌 허니팟 네트워크(Attacker Eye)에서 실제 공격 트래픽과 WAF 우회를 시도하는 페이로드 변이(Mutation)가 대량으로 포착되기 시작했다.[69]

왜? 비밀로 묶어 둘 약속이 세 번 새어, 고치기도 전에 공격이 먼저 도착했다.

시험 문제를 배포 전에 인쇄소·운송·창고에서 차례로 유출된 것과 같다. 원문이 적는 해커뉴스 게시, PoC 영상, Chainguard 이미지 조기 배포는 그 세 번의 유출이다. 여기서도 공격 코드 자체는 인용하지 않는다.

쉽게 풀어 쓴 비유 설명이며, 취약점에 관한 새로운 사실은 담고 있지 않다.

5. 글로벌 셧다운 도미노와 국내(한국) 웹 생태계의 특수 취약성[편집]

패치 배포 이전에 익스플로잇 방법론이 유출되자, 전 세계 정부 기관과 기업들은 해킹 피해를 막기 위해 패치가 완료될 때까지 아예 웹 서버를 인터넷에서 차단하는 초유의 ‘선제적 셧다운(Precautionary Shutdown)’ 도미노에 돌입했다.

5.1. 글로벌 공공 인프라 및 대형 서비스 중단 사태[편집]

미국 NSA와 유럽 CERT-EU, 영국 NCSC의 오프라인 전환 권고 직후 유럽 전역의 핵심 행정망이 일시 정지되었다. 네덜란드에서는 연방 정부 포털(Overheid.nl), 전자정부 인증 서비스(MijnOverheid, DigiD), 의회 웹사이트, 로테르담 항만청, 지역 병원 네트워크뿐만 아니라 사이버 보안 주무 기관인 네덜란드 국가사이버안보센터(NCSC-NL) 자체 홈페이지까지 접속을 차단했다(이 과정에서 외신 오보로 ‘네덜란드 전국 인터넷 차단’이라는 해프닝이 빚어지기도 했다). 핀란드 정부 IT 관리청(Valtori)은 핀란드 정부의 모든 대국민 웹 서비스를 오프라인으로 내렸으며, 프랑스 정부 포털(info.gouv.fr) 및 지방 행정 사이트, 덴마크의 전국 학교 소통 플랫폼(Kombit), 독일 프라이부르크 대학교 등도 시스템을 긴급 차단했다.[70]

민간 영역의 충격도 막대했다. 글로벌 인사·급여 플랫폼인 BambooHR은 미국, 캐나다, 아일랜드 전역에서 서비스를 일시 중단하며 기업들의 급여 처리 지연을 경고했고, 위키미디어 재단(Wikimedia Foundation)은 미디어위키 지원 도구와 Phabricator 인스턴스를 내렸다. 글로벌 PC 게임 플랫폼 스팀(Steam)은 상점과 홈페이지 접속이 한때 불능 상태에 빠졌으며, 오픈소스 방송 소프트웨어 OBS, GrapheneOS 포럼, 4chan, DeviantArt 등이 일제히 점검에 들어갔다.

특히 PHP 비중이 높은 일본 웹 생태계에서는 니코니코 동화, 픽시브(Pixiv·BOOTH·FANBOX), DMM, 메루카리(Mercari), DLsite를 비롯해 사이게임즈(우마무스메 프리티 더비, 그랑블루 판타지 버서스 라이징), 코나미(비트매니아 IIDX, 유비트), 세가의 아케이드 온라인 네트워크인 ALL.Net(마이마이, 츄니즘, 이니셜D 전체 아케이드 온라인 기능 정지), 페이트/그랜드 오더 고객센터, 포켓몬 홈 등이 일제히 긴급 서버 점검을 단행했다.[71]

5.2. 국내(한국) 웹 생태계의 구조적 취약성과 KISA 초기 대응 지연 논란[편집]

한국의 경우 대기업 및 공공기관의 기간계 웹 시스템이 자바(Java/Spring) 위주로 구축되어 있다는 통념 때문에 초기 경각심이 상대적으로 낮았으나, 실제 국내 인터넷 트래픽과 중소·중견기업(SMB) 인프라를 살펴보면 PHP에 대한 의존도와 취약성은 결코 낮지 않다.

한국시간 10월 21일 밤 11시 패치 공개를 전후하여 디시인사이드(이미지 및 동영상 서버), 에펨코리아(FMKorea), 더쿠(Theqoo), 인벤(Inven), 인스티즈(Instiz), 윗치폼, 가생이닷컴 등 국내 최대 규모의 트래픽을 처리하는 PHP 기반 커뮤니티들이 해킹 및 개인정보 유출을 막기 위해 일제히 긴급 접속 차단 및 점검에 돌입했다.[72]

더욱 심각한 구조적 뇌관은 한국형 CMS(그누보드·라이믹스) 및 영세 웹 호스팅 생태계에 자리 잡고 있다. 국내 수십만 개의 중소 쇼핑몰, 병원·의원 홈페이지, 학원, 언론사, 협회 및 일부 정부 산하 사이트들은 한국형 오픈소스 게시판/CMS 솔루션인 그누보드(GnuBoard), 영카트(YoungCart), 라이믹스(Rhymix, 구 XpressEngine) 및 워드프레스 기반으로 제작되어 있다. 이들 사이트의 상당수는 영세한 웹 호스팅(Shared Hosting)이나 오래된 단독 서버 환경에서 PHP 5.x 또는 PHP 7.x(특히 7.2~7.4) 버전을 그대로 사용하고 있다. 이번 취약점은 그누보드나 라이믹스 코드 자체를 수정해서는 절대 막을 수 없으며 서버의 PHP 엔진 바이너리를 교체해야만 해결되는데, 공유 호스팅 이용자는 서버의 PHP 버전을 직접 패치할 권한이 없고, 오래된 커스텀 PHP 5/7 코드를 사용하는 업체는 PHP 8.2 이상으로 업그레이드할 경우 사이트 문법 호환성이 깨져 화면이 먹통이 되는 딜레마에 빠져 있다.

이러한 위기 상황 속에서 한국인터넷진흥원(KISA)의 늑장 대응 또한 도마 위에 올랐다. 유럽 CERT-EU, 호주 ACSC, 일본 국가사이버통괄실 및 도쿄 경시청 등 해외 당국이 21일 낮부터 일제히 긴급 보안 경계령을 내리고 서버 오프라인 전환까지 권고한 것과 달리, 국내 민간 보안을 총괄하는 KISA 보안 공지 포털 ‘보호나라’에는 패치 배포 2시간 전인 21일 오후 9시까지도 PHP 관련 공지가 단 한 건도 올라오지 않았다. KISA는 10월 20일과 21일 낮 동안 F5, Adobe, 백업 솔루션 AhsayCBS 등 일반 보안 공지는 게시하면서도 정작 전 세계가 비상사태에 돌입한 PHP2Shell에 대해서는 22일 자정이 임박해서야 뒤늦게 대응 공지를 올려, 사전 유출 공격이 한창이던 골든타임 동안 국내 중소 웹 관리자들이 위협을 인지하지 못했다는 비판을 피하기 어렵게 되었다.[73]

PHP 코어 개발자 Gina Peter Banyard가 “유일한 완화책은 PHP를 패치하거나 업그레이드하는 것뿐”이라고 단언했듯, 설정 변경만으로는 모든 공격 경로를 완벽히 차단할 수 없다.[74] 그러나 즉시 업그레이드가 불가능한 레거시 환경을 위해 서버 엔지니어와 보안 담당자가 즉각 수행해야 할 표준 패치 절차와 임시 완화책, 그리고 절대 범해서는 안 되는 치명적 설정 함정을 명확히 숙지해야 한다.[75]

6.1. PHP 버전별 패치 매트릭스 및 숨겨진 번들 PHP 점검[편집]

패치를 적용할 때 가장 흔히 발생하는 실수는 디스크 상의 패키지만 업데이트하고 메모리에 상주 중인 워커 프로세스를 재시작하지 않는 것이다. 패치 후에는 반드시 systemctl restart php-fpm 또는 systemctl restart httpd/apache2를 실행하여 메모리에 로드된 구버전 바이너리를 교체해야 한다.[76] 또한 데비안(Debian), 우분투(Ubuntu), 레드햇(RHEL), 알마리눅스(AlmaLinux) 등 OS 배포판은 자체 백포트 패치를 제공하므로 버전 번호 문자열만 보지 말고 패키지 체인지로그(Changelog)에 CVE-2026-109618과 CVE-2026-109619가 포함되었는지 확인해야 한다.[77]

특히 RHEL/CentOS/AlmaLinux/Rocky Linux 환경에서 널리 쓰이는 서드파티 저장소인 Remi 저장소(rpms.remirepo.net)는 자원봉사자 유지보수 특성상 패치 당일 업데이트가 즉시 제공되지 않았으므로, 해당 저장소 사용자는 즉시 배포판 기본 모듈 스트림으로 전환하거나 소스를 직접 빌드해야 한다.[78] 아울러 서버 OS의 기본 PHP 외에 Plesk(sw-engine), cPanel, 하이퍼바이저 관리 솔루션인 VirtFusion(/opt/virtfusion/php8/bin/php), 윈도우용 XAMPP(php-cgi.exe)처럼 자체 내장(Bundled) PHP 엔진을 별도 경로에서 구동하는 상용 솔루션들을 전수 조사하여 개별 핫픽스를 적용해야 한다.[79]

6.2. 패치 불가 시 긴급 완화책(Workarounds)과 치명적인 설정 함정[편집]

당장 PHP 버전을 올릴 수 없는 환경에서 관리자들이 흔히 시도하는 대응 중에는 아무런 효과가 없거나 오히려 취약점 발동을 도와주는 세 가지 치명적인 설정 함정이 존재한다. 첫 번째 함정은 애플리케이션 내부의 ini_set() 함수나 PHP-FPM의 디렉터리별 .user.ini 파일을 통해 session.upload_progress.enabled=0을 설정하는 것인데, 이는 완전히 무용지물이다.[81] 멀티파트 파서(rfc1867.c)와 세션 업로드 진행률 핸들러는 .user.ini나 스크립트가 로드되기 이전에 먼저 실행되기 때문이며, 따라서 반드시 전역 php.ini 또는 FPM 풀 설정 파일(/etc/php-fpm.d/www.conf 등)에서 php_admin_flag[session.upload_progress.enabled] = off로 강제하고 모든 워커를 재시작해야만 효력이 발생한다.[82]

두 번째 함정은 리눅스 시스템 콜 수준에서 RLIMIT_AS(주소 공간 제한)나 RLIMIT_DATA를 사용하는 것이다. CVE-2026-109618의 OOM 베일아웃을 막기 위해 PHP 내부의 요청당 메모리 한도를 해제(php_admin_value[memory_limit] = -1)하는 조치가 권장되는데, 이때 단일 요청이 서버 전체 메모리를 고갈시키는 것을 막겠다며 RLIMIT_AS나 RLIMIT_DATA를 걸어버리면 한도 도달 시 커널이 mmap() 할당 실패를 반환하게 되며 이것이 곧바로 PHP의 취약한 longjmp() OOM 경로를 직접 트리거한다.[83] 따라서 OS 수준 메모리 제한이 필요할 때는 반드시 컨테이너나 cgroup의 memory.max 한도(문제가 된 워커 프로세스만 강제 종료하는 정책)를 사용해야 한다.[84]

세 번째 함정은 @ 연산자나 display_errors = Off, error_reporting = 0을 통해 경고를 숨기려는 시도다. CVE-2026-109619의 조기 INI 진단 소비자 경로는 화면에 에러를 출력하는지 여부와 무관하게 엔진 내부에서 진단 이벤트가 생성되는 순간 트리거되므로, 에러 표출을 숨기는 것은 아무런 방어 효과가 없으며 .htaccess나 웹 서버의 PHP_VALUE로 전달되는 구형·폐기(Deprecated) 설정 지시어 자체를 찾아내어 삭제해야 한다.[85] 아울러 최고 위험군인 아파치 mod_php(prefork MPM) 사용자는 즉시 기본 event MPM과 PHP-FPM 조합으로 전환하여 애플리케이션 실행 전 공격 경로를 차단해야 하며, 패치 대기 중인 서버는 앞단 Nginx나 Apache 설정에서 Content-Type: multipart/form-data 요청에 대해 즉시 HTTP 403 Forbidden을 반환하도록 차단하거나, 클라우드플레어(무료 플랜 포함 기본 적용 완료된 Full Transaction Detection 룰셋) 및 Imperva, 팔로알토 네트웍스(Threat Prevention 시그니처 543004) 등 엣지 WAF의 가상 패치(Virtual Patching) 뒤에 오리진 서버를 은폐해야 한다.[86][87]

7. 결론 및 전략적 시사점[편집]

현재 진행 중인 PHP2Shell(CVE-2026-109618·CVE-2026-109619) 사태는 단순한 서버 업데이트 권고 수준을 넘어, 전 세계 웹 인프라의 기저 계층(Runtime Layer)이 비인증 원격 코드 실행과 Heartbleed급 메모리 유출에 동시에 뚫린 최고 등급(Critical)의 사이버 비상사태다.[89] 특히 공격이 애플리케이션 코드 실행 이전에 이루어진다는 특성 때문에 소스 코드 무결성이나 애플리케이션 방화벽에 기대던 기존의 방어 논리는 완전히 무력화되었다.[90]

나아가 이번 사건은 사이버 보안 패러다임에 두 가지 중대한 이정표를 남겼다. 첫째, 프론티어 AI 모델(Gemini 4 Argon, GPT-5.6 Sol, Codex Security 등)의 발전으로 인해 지난 20년간 복잡성 뒤에 숨어 있던 C 언어 런타임의 난해한 메모리 관리 결함들이 단 며칠 만에 실전 RCE 무기로 변환되는 ‘AI 기반 취약점 발굴 및 무기화의 변곡점’이 도래했다는 점이다.[91] 오픈AI가 예고했듯 향후 수개월 내에 이와 유사한 레거시 오픈소스 코어의 대형 취약점들이 AI에 의해 연쇄적으로 발굴될 가능성이 매우 높다.[92] 둘째, 전 세계 PHP 서버의 60%~70% 이상을 차지하는 지원 종료(EOL) 버전(PHP 5.4~8.1)과 버전 정보를 숨긴 80%의 암묵적 자산들이 패치 사각지대에 남겨지면서, 패치 미적용 서버들을 노리는 랜섬웨어 그룹과 초기 침투 브로커(IAB)들의 자동화된 대규모 스캐닝 공격이 장기화될 것이다.[93]

따라서 각 조직의 보안 및 인프라 책임자는 인터넷에 노출된 모든 PHP 구동 자산(내장형 제어판 및 레거시 호스팅 포함)을 즉각 식별하여 PHP 8.2.35, 8.3.36, 8.4.27, 8.5.12 이상으로 엔진을 업데이트하고 워커 프로세스를 재시작해야 한다.[94] 동시에 패치 이전의 노출 창(Exposure Window) 동안 PHPSESSID 메모리 유출이나 OPcache 파일 읽기를 통해 이미 중요 자격 증명이 탈취되었을 가능성을 전제로 웹 서버 에러 로그와 코어 크래시 기록을 정밀 감사하고, 서버 내 저장된 데이터베이스 암호와 API 토큰, TLS 인증서 개인 키를 전면 교체(Rotation)하는 사후 침해 대응 절차를 병행해야 한다.[95]
